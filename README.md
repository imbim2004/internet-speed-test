# speedtest.py — замер скорости интернета

Делает N **последовательных** GET-запросов к указанному адресу (например, к тяжёлой картинке),
дожидается полного ответа каждого и печатает среднее время запроса, объём скачанных данных
и скорость в МБ/с.

Зависимостей нет — только стандартная библиотека Python 3.8+. Ничего устанавливать не нужно.

## Запуск

```bash
git clone https://github.com/imbim2004/internet-speed-test.git
cd internet-speed-test
python3 speedtest.py
```

Без аргументов берётся картинка ~9.7 МБ с Wikimedia. Свой адрес — первым аргументом:

```bash
python3 speedtest.py "https://ваш-сервер/большой-файл.jpg"
```

По умолчанию 10 запросов, меняется ключом `-n`.

## Тесты

```bash
python3 tests.py
```

14 тестов, около 3 секунд, **интернет не нужен**: поднимается локальный сервер, который
намеренно отдаёт битые ответы, и проверяется, что скрипт их распознаёт. Проверено на
Python 3.9.6 (штатный на macOS) и 3.14.6.

## Ключи

| Ключ | Значение | По умолчанию |
|---|---|---|
| `URL` | адрес, куда стучаться | картинка ~9.7 МБ с Wikimedia |
| `-n`, `--requests` | количество последовательных запросов | `10` |
| `-t`, `--timeout` | таймаут одной операции с сокетом, секунды | `60` |
| `--max-seconds` | предел длительности одного запроса целиком (`0` — без предела) | `300` |
| `--max-bytes` | предел объёма одного ответа, напр. `500M`, `2G` (`0` — без предела) | `512M` |
| `--warmup` | сделать прогревочный запрос, не учитываемый в статистике | выкл. |
| `--no-cache-buster` | не добавлять уникальный query-параметр к URL | выкл. |
| `-q`, `--quiet` | не печатать строку по каждому запросу, только итог | выкл. |

Коды возврата: `0` — замер выполнен, `1` — не удался ни один запрос, `2` — неверные аргументы,
`130` — прервано с Ctrl+C (статистика по уже выполненным запросам всё равно печатается).

## Как считается скорость

- Время запроса меряется от отправки запроса до чтения последнего байта тела ответа
  (`time.perf_counter()`), то есть включает DNS, TCP/TLS-хендшейк, TTFB и саму загрузку.
  Если по адресу есть редиректы, их время тоже входит в замер, а байты считаются только
  у финального ответа.
- Тело ответа читается потоком и не держится в памяти целиком — считаются только байты.
- **Скорость** = общий объём скачанного / суммарное время всех успешных запросов.
  Выводится и в МБ/с (мегабайты, 1 МБ = 1024² байт), и в Мбит/с (мегабиты, как у провайдеров).
- К каждому URL добавляется уникальный параметр `?_cb=<timestamp>-<номер>` и заголовки
  `Cache-Control: no-cache`, чтобы ответ не пришёл из кэша и замер был честным.
  Отключается ключом `--no-cache-buster` — он нужен, если сервер строго проверяет
  набор query-параметров (подписанные ссылки S3/CDN от лишнего параметра отдадут 403).
- Запрашивается `Accept-Encoding: identity`: иначе мерялась бы скорость передачи уже
  сжатого потока, а не объявленного объёма.
- Упавшие запросы (таймаут, DNS, HTTP-ошибка) не ломают прогон: они логируются в stderr,
  а статистика считается по успешным.

Файл стоит брать от ~5 МБ, иначе результат меряет в основном задержку соединения,
а не пропускную способность — скрипт предупредит, если средний ответ меньше 1 МБ.
Адрес должен отдавать один и тот же файл фиксированного размера; если размеры ответов
разъезжаются, скрипт тоже предупредит.

## Крайние случаи

Всё перечисленное закрыто тестами в `tests.py`.

- **Оборванный ответ.** Сервер обещает `Content-Length: 1000`, отдаёт 10 байт и закрывает
  соединение. При чтении по кускам исключения не возникает, поэтому такой ответ молча зачёлся
  бы как быстрый успешный запрос и **завысил** бы скорость. Объём скачанного сверяется
  с `Content-Length`, расхождение считается ошибкой.
- **Бесконечный поток.** Если по адресу не файл, а стрим, таймаут не срабатывает никогда —
  данные идут ровно. Ограничивается `--max-bytes`.
- **Медленная отдача по байту.** Каждая отдельная операция чтения укладывается в таймаут,
  но запрос тянется бесконечно. Ограничивается `--max-seconds`; чтение идёт через `read1()`,
  иначе проверка лимита не выполнялась бы, пока сервер не дошлёт весь кусок.
- **Некорректные аргументы.** Отрицательный, нулевой или `nan` таймаут, `-n 0`, URL без схемы
  или без хоста, `file://`, `ftp://` — отсекаются с внятным сообщением, а не трейсбеком.
- **Кириллические и IDN-адреса** (`https://пример.рф/файл.jpg`) — хост кодируется в IDNA,
  путь и query процентно-кодируются без повторного экранирования уже закодированного.
- **Ctrl+C** посреди прогона — печатает статистику по уже выполненным запросам, код возврата `130`.
- **Обрыв соединения, редирект-петля, просроченный TLS-сертификат** — обрабатываются как
  обычные ошибки запроса.

## Безопасность

- **Проверка TLS включена** (умолчание `urllib`): просроченный или неподходящий сертификат
  приводит к ошибке запроса, а не к молчаливому скачиванию. Отключения проверки в скрипте нет.
- **Схемы ограничены `http`/`https`** — и при разборе аргумента, и при редиректах. Штатный
  `HTTPRedirectHandler` разрешает ещё и `ftp://`, то есть проверку аргумента можно было обойти
  одним 302-ответом; скрипт подменяет обработчик и обрывает такой редирект.
- **Вывод сервера очищается от управляющих символов.** Текст статуса ответа контролируется
  сервером, и ANSI-escape из него попадал прямо в терминал — этим можно затереть строки вывода
  и подделать, например, итоговую цифру скорости. Все строки от сервера фильтруются
  и обрезаются по длине.
- **Пароль из URL** (`https://user:pass@host/file`) маскируется при печати, чтобы не утекал
  в логи прогона.
- **Ответы не сохраняются на диск** и не парсятся — только считаются байты.
- Тело ответа закрывается и при ошибке HTTP: иначе при большом `-n` на отвечающем ошибкой
  адресе копились незакрытые дескрипторы.
- Скрипт учитывает переменные окружения `http_proxy` / `https_proxy` (поведение `urllib`).
  Если они заданы, вы меряете скорость до прокси, а не до целевого хоста.

## Замечания

- Первый запрос обычно медленнее остальных: холодный DNS, TLS-хендшейк, прогрев соединения
  и кэша CDN. Ключ `--warmup` делает отдельный прогревочный запрос, чтобы это не смазывало
  статистику: на одном и том же канале разброс времени запроса без него был 8.5–26 с,
  с ним — 3.9–4.7 с.
- Замер однопоточный и последовательный — по ТЗ. Это показывает скорость **одного** соединения,
  которая обычно ниже пиковой скорости канала: многие сервера ограничивают отдачу на соединение.
